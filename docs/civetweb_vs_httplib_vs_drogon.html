3️⃣ API 编写对比

同等功能的三方代码对比：GET /api/hello + WebSocket /ws

CivetWeb (C API + C++ 封装)cpp-httplib (C++11)Drogon (C++17)
 
// 1. 启动服务器
mg_callbacks cb = {0};
cb.log_message = logFn;
struct mg_context *ctx = mg_start(&cb, 0, opts);

// 2. 注册路由 (C 风格回调)
mg_set_request_handler(ctx, "/api/hello", [](mg_connection *conn, void *){
  mg_printf(conn, "HTTP/1.1 200 OK\r\n"
    "Content-Type: text/plain\r\n"
    "Content-Length: 13\r\n\r\n"
    "Hello, World!");
  return 200;
}, nullptr);

// 3. WebSocket 注册
mg_set_websocket_handler(ctx, "/ws",
  wsConnectFn, wsReadyFn, wsDataFn, wsCloseFn, nullptr);
    
// 1. 创建服务器对象
httplib::Server svr;

// 2. 路由注册 (C++ lambda)
svr.Get("/api/hello", [](const auto& req, auto& res) {
  res.set_content("Hello, World!", "text/plain");
});

// 3. WebSocket
svr.set_ws_handler("/ws", [](auto& req) {
  return std::make_shared();
});

// 4. 启动
svr.listen("0.0.0.0", 8080);
    
// 1. 控制器类 (OOP)
class HelloCtrl : public HttpController<HelloCtrl> {
public:
  METHOD_LIST_BEGIN
    METHOD_ADD(HelloCtrl::hello,
      "/api/hello", Get);
  METHOD_LIST_END
  void hello(const HttpRequestPtr& req,
             std::function&& callback) {
    auto resp = HttpResponse::newHttpResponse();
    resp->setBody("Hello, World!");
    callback(resp);
  }
};

// 2. WebSocket 控制器
class WsChat : public WebSocketController<WsChat> {
  void handleNewMessage(...) override;
};

// 3. 启动
int main() {
  app().addListener("0.0.0.0", 8080).run();
}

6️⃣ 核心优缺点总结

👍 CivetWeb 优点

  • MIT 许可，商业友好无传染性
  • 零外部依赖，仅需标准 C 库
  • 内置 HTTP + HTTPS + WebSocket + 文件服务
  • 成熟稳定，生产验证 10+ 年
  • 跨平台 (Win/Linux/macOS/嵌入式)
  • 32/64 位都支持
  • 资源占用极低 (~2-4 MB)

👎 CivetWeb 缺点

  • C 语言 API，与 Qt 项目有代码风格落差
  • 需写 ~115KB C++ 封装层桥接
  • 线程模型僵化，长连接占用线程资源
  • 不支持 HTTP/2、SSE
  • 无路径参数、中间件等高级路由
  • 维护活跃度近年下降
  • 高并发场景性能天花板低

👍 cpp-httplib 优点

  • 单头文件 header-only，集成成本为零
  • 现代 C++11 lambda API，代码极简
  • MIT 许可，商业友好
  • 功能全面：HTTP/HTTPS/WebSocket/SSE/流式
  • 支持路径参数路由 /users/:id
  • 三种 SSL 后端可选 (OpenSSL/MbedTLS/wolfSSL)
  • 资源占用最小 (1.3 MB 空载)
  • 文档详尽，示例丰富

👎 cpp-httplib 缺点

  • 不支持 32 位平台 (硬伤)
  • 阻塞式 Socket I/O，高并发受限
  • 每个 WebSocket 连接独占一个线程
  • 仅支持 HTTP/1.1，不支持 HTTP/2
  • QPS 极低 (91 QPS Hello World)
  • 复杂正则可能导致栈溢出
  • 不适合大规模并发连接

👍 Drogon 优点

  • 性能最强 (162K QPS Hello World)
  • 非阻塞异步 I/O (epoll/kqueue)
  • 支持 C++20 协程
  • 支持 HTTP/2
  • 内置 ORM、JSON、过滤器、AOP
  • WebSocket 不占线程 (事件驱动)
  • 高并发扩展性好 (10K 并发 44K QPS)
  • MIT 许可 + 活跃社区

👎 Drogon 缺点

  • 重框架，二进制 1.9 MB + 多依赖
  • 与 Qt event loop 集成困难
  • 学习曲线较陡 (需理解框架架构)
  • 全盘重写架构，迁移成本极高
  • NetShare 场景"大材小用"
  • ORM 等内置功能对于本项目无用
  • 侵入性强，改造现有代码工作量大

8️⃣ 结论与推荐

🏆 现用最优

CivetWeb
当前方案完全满足 NetShare 的局域网文件分享需求。
✅ 建议保留

📦 最佳替代

cpp-httplib
如果需要简化构建和 API，且无需 32 位支持。
⚡ 可迁移

🚀 极致性能

Drogon
性能最强，但迁移成本高，不适合 NetShare 当前场景。
🔧 大项目选择

最终建议

时间线建议原因
短期 (现在)保持 CivetWeb功能满足、零成本、无风险、与 Qt 兼容性好
中期 (半年内)评估 cpp-httplib如果项目不需 32 位，httplib 可大幅简化构建和 API
长期 (项目扩展)Drogon 备选只有 NetShare 发展成大规模并发服务时才考虑
